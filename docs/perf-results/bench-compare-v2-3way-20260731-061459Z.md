## Harness corrections applied after the run

Two numbers in the generated tables below are **wrong as printed** and are
corrected here. Both are capture artifacts, not broker behaviour.

1. **`consume-group` / skafka-go.** `run_job` captures pod output with
   `kubectl logs --tail=60`. The Go broker emitted 3,660
   `Received unrequested topic or partition kperf-bench-0 …
   (OffsetsForLeaderEpochUtils)` warnings, which pushed the
   `kafka-consumer-perf-test` CSV rows out of the last 60 lines on 3 of the
   4 pods. The parser surfaced this itself as `pods: 1` vs `pods_total: 4` —
   that mismatch is the tell. Recomputed from full pod logs:

   | --- | ---: | ---: | ---: | ---: | ---: |

   | records/s [sum] run-avg | 103756 | 94486 | 100130 | 1.10x | 0.94x |

   So Go trails Rust by ~10% on grouped-consumer throughput — not the
   3.90x the uncorrected table claims.

2. **`rebalance-scaleup` / skafka-go** is `N/A` for a different reason, and
   the `N/A` is real. Recomputing from full logs still yields **0 of 4**
   pods with data: every member printed the CSV header and then nothing,
   with no error line. kaas read 4,056,896 records and strimzi 2,801,570 on
   the same job. The consumer sets `auto.offset.reset=earliest` on a
   per-Job (controller-uid) group id, so this is not the stale-committed-
   offset trap. Cause unexplained — needs a dedicated investigation, not a
   perf conclusion.

### Topic-parity caveat

kaas's `kperf-bench` held **15,978,688** records against 15,000,000 on the
other two — exactly one partition's worth (978,688) of pre-run data that
survived the `kafka-topics --delete` used to level the three stacks before
the run. kaas therefore had ~6.5% more data available to read. That does
not account for the ~10% consume-group gap, but it does mean kaas's consume
figures are mildly flattered, and a topic delete leaving 1 of 16 partition
directories behind is itself worth chasing.

**Why skafka-go fails — and it is not the reason predicted.** The expected
cause was gh #219 (topic delete→recreate inheriting the prior incarnation's
state, fixed in v0.2.14-preview, well after v0.1.169). The kept runner log
(`streams-skafka-go-runner-20260731-061459Z.log`, 641 KB, essentially all
one repeated line) shows something else:

```
WARN OffsetsForLeaderEpochUtils - Attempt to fetch offsets for partition
     streams-plaintext-input-0 failed due to: Topic deletion is disabled., retrying.
```

The Go broker answers **OffsetForLeaderEpoch (API key 23)** with an error
code the client decodes as `TOPIC_DELETION_DISABLED` — nonsense for that
API — so the Streams client retries forever and the topology never produces
output. The runner burned all 290 s in this loop.

This is the same API behind the `consume-group` warning flood (3,660
`Received unrequested topic or partition` on skafka-go; **0** on both kaas
and strimzi), which makes one broken API the likely single root cause of
both the streams FAIL and the ~10% grouped-consumer shortfall: every
rejected response is a wasted round trip. It is a genuine Kafka 3.7 wire
defect in the Go implementation that the Rust rewrite does not have, and
the produce benchmarks cannot see it because produce never touches key 23.
